# 质控整改闭环与批量质控 · 设计与实现

> 对应代码：`server/src/qc/`、`server/src/routes/records.js`、`web/src/views/RecordDetailView.vue`、`web/src/views/RecordsView.vue`

## 1. 要解决的问题

单次 AI 质控只能回答“这份病历现在多少分”。真实病案管理关心的是：

1. 医生有没有按建议改？
2. 改完分数有没有提高？
3. 改了哪些字段、哪条问题被解决？
4. 一批病历能不能一次性跑完、跑失败能不能定位？

因此本次在原有“单条质控”之上补了三层能力：**版本留档 → 整改对比 → 批量执行**。

---

## 2. 数据模型

### 2.1 `record_versions`：每轮质控的正文快照

| 字段 | 说明 |
| --- | --- |
| `record_id` + `version` | 同一病历内版本号从 1 递增，唯一键防并发重复 |
| `snapshot` | 7 个正文字段的 JSON 快照（主诉/现病史/既往史/查体/辅助检查/诊断/处理意见） |
| `dimensions` | 当轮四维得分快照 |
| `score` / `level` | 当轮总分与等级 |
| `report_id` | 对应 `qc_reports.id` |
| `source` | 目前为 `qc`，预留手工留档 |

写入时机：`evaluateRecord()` 在质控报告落库后立即写版本。快照只存正文，不存 `status`、`updated_at` 等易变字段，避免 diff 出现噪声。

### 2.2 `qc_reports` 的分差字段

| 字段 | 说明 |
| --- | --- |
| `prev_score` | 上一份报告分数（没有则为 NULL） |
| `score_delta` | 本次 − 上次 |
| `record_version` | 本次对应的版本号 |

由 `evaluateRecord()` 在插入报告前查询上一份报告计算，列表页/详情页/时间线直接消费，不需要前端二次计算。

### 2.3 批量任务表

- `qc_batches`：任务级汇总（总数、完成、失败、提升数、平均提升、状态、起止时间）；
- `qc_batch_items`：每份病历的明细（状态、分数、等级、报告 ID、耗时、失败原因）。

两张表都带 `created_at`，便于后续做“批量质控使用率”统计。

## 3. 一次质控的完整链路

```
POST /records/:id/qc
  → 读取 medical_records
  → getRules()：从 qc_rules 读启停/权重/严重度（10s 缓存）
  → runQC(record, { rules })
       ├─ 未配置 Key / 调用失败 → localQC() 规则引擎（按规则编码扣分）
       └─ DeepSeek → normalizeQC() → applyRulePolicy()
              ├─ matchRuleCode() 把 AI 的问题码语义对齐到规则库
              ├─ 停用规则过滤
              └─ 严重度以管理端配置为准
  → 查询上一份报告分数 → prevScore / scoreDelta
  → INSERT qc_reports（含分差）
  → createVersion() 写快照
  → UPDATE medical_records.status（≥80 通过，否则不通过）
  → 返回 reportId / score / version / prevScore / scoreDelta
```

### 3.1 为什么 AI 问题码要“语义对齐”

大模型偶尔会把“主诉与现病史不符”也标成 `C-001`（主诉缺失）。如果直接按编码套规则严重度，就会把逻辑问题误判成严重缺项。`matchRuleCode()` 的顺序是：

1. 编码与规则名称一致 → 直接用；
2. 用关键词重新归类（主诉/现病史矛盾 → `L-001`，诊断+ICD → `A-001`，术语/表述 → `T-001`……）；
3. 完整性问题区分“整段缺失”和“写得太简/缺项”；
4. 无法归类 → `AI-001`，不硬套规则。

这样规则页的停用/调权重对 AI 结果才是可信的。

## 4. 整改对比 API

### `GET /records/:id/versions`

返回版本列表（倒序），用于时间线/轮次展示。

### `GET /records/:id/versions/compare?from=1&to=2`

不传 `from/to` 时默认对比最近两个版本。返回：

```json
{
  "from": { "version": 1, "score": 42, "level": "D", "dimensions": {...} },
  "to":   { "version": 2, "score": 88, "level": "B", "dimensions": {...} },
  "scoreDelta": 46,
  "changedFields": ["present_illness", "past_history"],
  "changes": [
    { "field": "present_illness", "label": "现病史", "before": "...", "after": "...", "changed": true }
  ]
}
```

前端在病历详情页把 `scoreDelta`、四维变化、字段 diff 直接渲染成“整改闭环”卡片；问题清单里 `field` 命中 `changedFields` 的会显示“本轮已修改”。

## 5. 批量质控

### 接口

- `POST /records/batch-qc` `{ "recordIds": [17, 31] }` → `{ batchId, total, skipped }`
- `GET /records/batch-qc/:id` → 进度 + 明细

### 执行策略

- 单次最多 20 份；临床医师只能操作本人病历；
- 已在 `queued/running` 任务中的病历会跳过，避免重复调用与版本号竞争；
- 进程内并发 2（`CONCURRENCY = 2`），平衡 2 核服务器压力与大模型延迟；
- 每条完成立即回写 `done/failed`，前端 1.5s 轮询即可看到进度；
- 任务异常 → 批次 `failed`，未执行明细标记失败原因；
- 服务重启 → `recoverInterruptedBatches()` 把遗留的 `queued/running` 收尾，前端不会永远转圈。

### 前端交互

病历列表支持多选 → “批量质控（n）”→ 弹窗显示进度条与逐条状态；任务完成后自动刷新列表，未关闭窗口可继续“后台运行”。

## 6. 规则热生效

- `getRules()` 缓存 10 秒；
- `PUT /rules/:id` 成功后调用 `invalidateRules()`，下一次质控立即用新配置；
- 规则引擎：停用规则不扣分、不出问题；权重按 `当前权重 / 默认权重` 缩放扣分；
- AI：停用规则的问题会被过滤，严重度按配置覆盖；
- `GET /rules/usage` 统计近 30 天每条规则命中次数，规则页展示为“近 30 天命中”。

## 7. 导出

### 质控报告（打印 / PDF）

前端路由 `/records/:id/report`，独立 A4 排版；`window.print()` 后选择“另存为 PDF”。不依赖服务端 PDF 库，部署零额外依赖。

### 病历清单 CSV

`GET /records/export.csv`：

- 复用列表筛选条件与临床医师数据权限；
- UTF-8 BOM，Excel 打开不乱码；
- 字段：患者、病案号、性别、科室、医师、诊断、状态、质控分、等级、最近质控时间、更新时间。


当前演示库中，病历 27（孙丽娟）已走完一轮闭环：42 分 D → 补全现病史、查体、检查、诊断与处理意见 → 88 分 B，`+46` 分，7 个字段有 diff。看板“整改闭环”卡片会显示待整改、复评通过率与平均提升。

> 重新执行 `npm run db:seed` 会重置演示数据（版本表也会清空）；想复现闭环，在病历详情按建议修改后点“重新质控”即可。AI 评分存在模型波动，同一份病历重复质控分数可能小幅变化；版本对比记录的是“当轮实际得分”，不会为了好看而回填。

## 9. 与人工复核、整改任务的关系

版本对比记录的是“每一轮实际质控的分数”。医院落地时还叠加两层治理：

- **人工复核/改判**：`qc_reports.final_score` 才是最终分；复核通过/改判会同步 `medical_records.status` 与整改任务；
- **整改任务**：AI 分 <80 自动建单，复评 ≥80 或人工复核通过自动关闭；工作台按逾期优先排序。

这两层不替换版本对比，而是让版本差异成为“整改是否有效”的客观证据。详见 [医院落地.md](医院落地.md)。
